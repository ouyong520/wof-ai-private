# Alpha PM Dispatch Builder Protocol V1

Status: authoritative helper protocol for C4-generated Alpha PM → Worker dispatch packages.

Scope: PM/Worker coordination only. It does not authorize Alpha runtime/product changes and does not apply to Collector, Unified Collector, or Training Farm / 10训.

## 1. Purpose

`parallel/PM/tools/alpha_pm_dispatch_builder.py` converts one compact 1–3 worker JSON spec into the durable communication package required by `parallel/PM/ALPHA_PM_DISPATCH_CONTRACT_V1.md`:

- normalized worker start prompts;
- one final immutable `wof-alpha-dispatch-manifest-v1` manifest;
- deterministic per-worker RESULT JSON/Markdown paths;
- short chat handoffs for presentation only;
- fail-closed C2/C3 preflight before anything is written.

The builder imports `parallel/PM/tools/alpha_worker_dispatch_contract.py`. It does not replace or weaken C2/C3 validation rules.

## 2. Compact spec

Use `parallel/PM/schemas/alpha_dispatch_spec_v1.schema.json` and start from `parallel/PM/templates/alpha_dispatch_spec_v1.json`.

Required dispatch fields are `schema`, `dispatchId`, `createdAtUtc`, `authorityPath`, `authorityCommit`, and `workers`. `createdAtUtc` is supplied by PM rather than generated by the builder so repeated rendering of the same spec is byte-deterministic.

Each worker requires `stageId`, `dedupKey`, and a short `mission`. The builder defaults `dedupProtocol` to `v2` and `dedupMode` to `exclusive`; explicit values are verified. `promptPath` may be omitted, in which case it is deterministically `parallel/PM/<stageId>_START_PROMPT.md`.

`resultJsonPath`, `resultMdPath`, `resultProtocol`, and `terminalCommitPrefix` may be omitted because they are derived from the C2/C3 contract. If supplied, they are assertions and any drift fails closed.

For `independent-validation`, both PM-assigned independent-validation identifiers are mandatory.

## 3. Deterministic derived contract

For each worker `<stageId>`:

- RESULT JSON: `parallel/PM/RESULTS/<stageId>_RESULT.json`
- RESULT Markdown: `parallel/PM/RESULTS/<stageId>_RESULT.md`
- terminal prefix: `WORKER_RESULT <stageId>`
- manifest slot: input order, exactly `1..N`

The final manifest path is `parallel/PM/DISPATCH_MANIFESTS/<dispatchId>.json`. A supplied `manifestPath` must equal that exact path.

Prompts explicitly distinguish immutable PM handoff artifacts (prompt + manifest) from per-stage Worker RESULT artifacts. Generated chat handoffs repeat the contract's minimal terminal policy: COMPLETE / SUBCOMPLETE / precise BLOCKED.

## 4. Fail-closed preflight

The builder rejects worker counts outside 1..3, duplicate identities/results, malformed or traversal paths, missing/malformed authority, unsupported dedup metadata, redirected RESULT paths, unknown mutable status/dashboard fields, and existing output targets.

After normalization it runs the existing C2/C3 in-memory validators against the final manifest and every generated prompt/manifest pair. Any validator error prevents render/build success.

When `--repo-root` is provided (default `.`), `authorityPath` must exist as a file beneath that repository root.

## 5. Commands

Validation only; writes nothing and does not care whether generated authority targets already exist:

```text
python parallel/PM/tools/alpha_pm_dispatch_builder.py validate SPEC.json --repo-root .
```

Render the deterministic package as JSON; writes nothing:

```text
python parallel/PM/tools/alpha_pm_dispatch_builder.py render SPEC.json --repo-root .
```

Create prompts + manifest beneath an explicitly supplied output root:

```text
python parallel/PM/tools/alpha_pm_dispatch_builder.py build SPEC.json --repo-root . --output-root ./staging
```

`build` is create-only. If any target already exists, the command fails before ordinary writes. A race that creates a target during the write phase also fails closed; there is no claim of a multi-file transaction.

Every command prints one JSON object. Success has `"ok": true`; failure has `"ok": false`, returns exit code 2, and includes exact errors.

## 6. Dispatch rule

PM may send the generated short chat only after the package validates. Once dispatched, the prompt and manifest are immutable authority. Worker progress and terminal state are written only through the declared per-stage RESULT files and other task-authorized implementation files; workers never rewrite the manifest as a status board.
